## 依頼を手順へつなぐ {#skill-poteto-mode}

原文：{{src:skills/poteto-mode/SKILL.md}}、{{src:docs/guide/02-poteto-mode.md}}。

`/poteto-mode` は、目的を受け取り、23個のプレイブックから仕事に合うものを選びます。原則一覧を読み、該当するプレイブックの手順をTODOの先頭へそのまま転記し、必要な段階で他のスキルを呼びます。実行しない段階も消さず、理由を記します。

一度入ると会話中は有効なモードとして続きます。毎回コマンドを繰り返す必要はありません。別の仕事へ移る場合は `new task` と明示すると、前の作業の続きを前提とせず、プレイブックを選び直せます。

## 目的を伝える

「機能を追加する」と「仕組みを調べる」では、コード変更の有無が違います。「調べるだけ。まだ変更しない」と書けば、読み取り中心の `investigation` を選ぶ根拠になります。実装の手段だけを指定するより、利用者に見える動作と制約を示すほうが手順を選びやすくなります。

| 依頼の性質 | 主な入り口 |
| --- | --- |
| 現状や理由を知りたい | `investigation` |
| 不具合が再現する | `bug-fix` |
| 新しい動作が必要 | `feature` |
| 動作を変えず構造を直す | `refactoring` |
| 測定した遅さを改善する | `perf-issue` |
| 既存手順に収まらない大きな仕事 | `figure-it-out` |
| 数日以上続くプログラム全体 | `orchestrate` |

## 共通の判断

境界を越える実装では先に `architect` を使い、型や責務を決めます。仮説を確かめる変更と、検証の証拠を対応させます。レビュー前にはコメントと文章も整えます。原則の名前を挙げるだけでなく、その原則がどの判断を変えたかを説明する契約です。

複数の作業を並べる場合はブランチとworktreeを分けます。サブエージェントの終了報告だけで判断せず、親が差分を読み、自分の言葉で結果を報告します。原文のモデル既定値より、`setup-pstack` の役割別設定が優先します。

## 自律性の読み方

原文は、可逆な作業を進め、不可逆な書き込みでは一度止まる姿勢を定め、さらにセッションの指示による上書きも説明しています。これはpstack内の運用規則です。個々のサービスや実行環境の権限を新たに与えるものではありません。

> **解説（本書の解釈。原文の規定ではありません）**
>
> 長時間任せる場合は、「ローカル変更とコミットまで」「PRを開くまで」「マージまで」を依頼に書き分けると、完了条件と権限の範囲を読み合わせやすくなります。

## 報告で確認する点

報告は、利用者に何が変わるかを先に説明し、次に保守する人が引き継ぐ構造と検証を示します。観測、推論、推測を混ぜません。リンクは実際に読んだ、または作成した成果物に限ります。簡潔さを理由に、トレードオフや未解決事項を落とさないことも原文の要件です。
