# PRプレイブック

PRを開く、マージ可能に整える、実際にマージする、という三つの仕事を分けます。CIが成功しているだけで、独立した動作検証やマージの権限がそろったことにはなりません。

## レビューできるPRを開く：opening-a-pr {#playbook-opening-a-pr}

原文：{{src:skills/poteto-mode/playbooks/opening-a-pr.md}}。

変更は原則としてmainから分けたworktreeで行い、コミットを小さく、順序立てて整えます。無関係な作業を混ぜません。`cursor-team-kit` の `deslop`、pstackの `no-comments`、`technical-writing`、`unslop` で差分と文章を整えます。`deslop` は別プラグインです。

タイトルは `type(scope): subject` のConventional Commits形式です。本文は作業日誌ではなく、変更の必要性、範囲、選択、影響、証拠を説明する短い資料にします。原文の節は `Why`、`Scope`、`Tradeoffs`、`Blast Radius`、`Verification` で、不要な節は省けます。大量の測定表や実行記録は別の証拠へリンクします。

操作先は最初に決めます。既定はGitHub CLIの `gh` です。`origin` コマンドがあり、対象リポジトリを解決できる場合はOriginを優先します。その選択を作成、閲覧、監視、編集、マージで維持します。通常のPR手順はGraphiteを要求しません。

スタックでは、根のPRだけがtrunkを対象にします。子は親の正確な先端へ載せ、PRのbaseも親ブランチにします。独立した仕事だけをtrunkから分けます。原文の標準手順はdraftではなくreadyで開きます。

PRを開いたことだけでは `babysit` は始まりません。まず作業の段階やスタックを完成させ、依頼があったときに監視を始めます。ただし `autopilot-full` と `autopilot-stack` の担当者には、最初から監視まで割り当てる例外があります。

## マージ可能まで整える：babysit {#playbook-babysit}

原文：{{src:skills/poteto-mode/playbooks/babysit.md}}。

最初にモードを決めます。

| モード | 用途 |
| --- | --- |
| `drive` | マージ可能になるまで進める |
| `background` | 本来の作業を止めずに仕分ける |
| `threads-only` | レビューへの対応だけを行う |
| `check` | 一度状態を確認して報告する |

小さいPRや文書のみのPRは `check` を使います。スタックには監視担当を一人だけ置き、最下位の未マージPRを優先します。処理順は競合、レビューのスレッド、CIです。既知の修正を一回のpushへまとめます。

通常の監視担当はbase変更、rebase、force-pushなどのスタック構造を変えません。競合があれば、どのブランチをrebaseすべきかを責任者へ報告します。自分のPRを所有するautopilot担当には原文で別の扱いがあります。

GitHubでは同梱の `scripts/watch-pr/watch-pr` を使います。`--status-only` は一度の状態確認です。単独・通常スタックでは `READY` が停止点です。キュー形式では `READY` を出さず、`WAITING` と理由 `merge-queue` が出たら、マージ可能と報告して監視を止めます。Originの状態へGitHub固有の判定語を持ち込みません。

CIを再実行する前に失敗を分類します。不安定なテストや基盤障害なら新しいビルドを一度試し、同じ失敗を繰り返したら分類を見直してログを読みます。変更していないコードの失敗では、古いbaseかを確認します。

レビューコメントは命令ではなく、コードに照らして検証する情報です。実際の問題は修正し、誤検知は反証を示します。ボットを黙らせるためだけにコードを動かしません。詳細な判断基準は {{src:skills/poteto-mode/references/bugbot-triage.md}} にあります。

この手順の終了は「マージ可能」です。マージや自動マージの設定には、マージする明示的な依頼が必要です。緑のチェックや監視の再開は、その代わりになりません。

## 検証済みの範囲をマージする：shipping {#playbook-shipping}

原文：{{src:skills/poteto-mode/playbooks/shipping.md}}。

PRごとに、実装者と異なる検証担当が親とheadを比較し、実際の画面やCLIで確かめます。判定は `PASS`、`PASS+NOTES`、`FAIL` です。CI成功やボット承認だけを、この独立検証の代わりにしません。

最下位の未マージPRから、合格判定が連続する範囲だけを対象にします。下に未検証PRがある場合、上のPRだけ合格していても先へ進みません。検証済み範囲の上限と、連続性を切っているPRを示します。

### 検証した差分と現在の差分を対応させる

判定時のhead SHA、base SHA、baseからheadへの安定した `git patch-id` を記録します。rebaseやbase変更後はSHAだけでは対応を判断できないため、現在の差分と比較します。同じ差分ならコードの判定を保持しつつ、現在のheadでCIとマージ可能性を確認します。差分が変われば原則として再検証します。

原文には、変更がテスト・文書・lint設定だけに限られる場合の詳細な再利用規則もあります。判定時のビルドを二回、現在のheadを一回作り、再現するノイズや埋め込まれたコミットSHAの差を個別に判定します。ビルド成果物のない開発サーバーの結果はこの規則で再利用できません。適用する際は原文の第3段階を確認します。

### 一つずつ進める

最新trunkを取得し、最下位PRだけを準備して必要ならrebaseとbase変更を行います。その変更後にも判定の有効性を確かめます。一つをsquash mergeし、実際のマージを確認してから次を準備します。子孫全体に先回りして自動マージを設定しません。

GitHubの `autoMergeRequest` は、そのPRに自動マージが要求されたことを示すだけです。スタック全体の準備や検証の有効性を証明しません。マージ後にtrunkを取得し、結果のSHA、次のPRのbase、head、CI、patch-idを読み直します。

`babysit` と違い、キュー待ちで仕事は終わりません。現在の最下位PRが実際にマージされたか、停止すべき失敗になったかを監視します。検証済みの連続範囲が終わったら、届いた変更と次の検証の欠落を報告します。
