# why：設計の理由を調べる

## 動機と制約を探す {#skill-why}

原文：{{src:skills/why/SKILL.md}}、{{src:skills/why/references/epistemics.md}}、{{src:skills/why/references/synthesizer-prompt.md}}。

`/why` は、コードの形を生んだ判断、制約、トレードオフを調べます。現在の動作から理由を想像するだけではなく、コミット、PR、文書、会話、運用記録をたどります。

最初に対象のパス、行、シンボル、関連コミットとPRを集めます。`git blame` だけで結論にせず、`git log --follow -p` で名前変更を含む履歴を読み、PR本文や議論へ進みます。最新の変更が最初の理由とは限りません。

## 七つの証拠カテゴリ

| カテゴリ | 得られる主な根拠 |
| --- | --- |
| ソース管理 | 実装時の理由、レビュー、テスト |
| 課題管理 | 利用者の要求、業務上の制約 |
| 長文ドキュメント | 設計案と事前の比較 |
| チームの会話 | 文書化されなかった議論 |
| インフラの観測 | タイムアウトや負荷などの現実 |
| エラー追跡 | 例外の発生経路、回帰 |
| 分析用データ | 閾値、実験、機能公開の判断 |

接続済みMCPを実行時に見つけ、証拠カテゴリへ対応づけます。原文はソース管理を必須の調査源としています。他のカテゴリは利用可能な接続に応じて調べます。調査担当はMCPを使えるエージェントモードで動かしますが、記録への書き込みはしません。「読み取り専用モード」と「書き込みをしない調査」は同じ指定ではない点に注意します。

## ない情報も結果に含める

検索して該当なしだった場合、接続がなく検索できなかった場合、対象との無関係を証明して省略した場合を分けて記録します。「たぶん関係ない」は省略の根拠になりません。防御的なコードを調べる場合は障害や事後分析の観点も加えます。

統合結果では、分かったこと、合理的に推論できること、競合する仮説、分からないこと、参照先、確信度を分けます。親が文章を整える場合も、確信度の表現は維持します。

> **例（本書独自の例。原文にはありません）**
>
> `/why 再試行上限を5回にした理由を調べてください。決定時の根拠と、現在も成り立つ制約を分けて示してください。`

変更に向けた調査なら、最後に「維持すること」「変えること」「避けること」「リスク」へ整理します。歴史を知るだけでなく、次の設計が守るべき条件へつなげるためです。
