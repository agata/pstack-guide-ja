# interrogate：複数モデルで差分を疑う

## レビューの契約 {#skill-interrogate}

原文：{{src:skills/interrogate/SKILL.md}}、{{src:skills/interrogate/references/rubric.md}}、{{src:skills/interrogate/references/code-quality-review.md}}、{{src:skills/interrogate/references/lead-judgment.md}}。

`/interrogate` は、複数モデルに同じ差分、意図、評価基準を渡すレビューです。役柄を変えて演じさせるより、モデルの違いから盲点を探します。成果物は統合した判定であり、指摘を自動で修正するスキルではありません。

最初に範囲を定めます。指定ファイル、明示された差分、または作業ブランチ全体を適切なbaseと比較します。次に利用者の依頼、コミット、PR本文、コードから変更の意図を一段落で明示します。意図が不明なら、レビューを始める前に確認します。

## 独立した指摘を集める

`interrogate reviewers` の設定一項目につき一人の読み取り専用担当を起動します。全員が同じ文脈とコード品質の観点を受け取ります。複数モデルが独立に挙げた問題は強い信号ですが、一人だけの発見も読みます。重複はまとめ、意見の対立は消さずに残します。

親は単なる集計役ではありません。実際の目的と費用を踏まえて、すべての指摘を次の四つへ分類します。

| 分類 | 意味 |
| --- | --- |
| `Act on` | 正しさ、安全性、保守性に実際の問題があり、対処すべき |
| `Consider` | 妥当だが、今直す費用に見合うか判断が必要 |
| `Noted` | 技術的には正しいが、現状では行動につながらない |
| `Dismissed` | 誤り、細部への過剰な指摘、文脈不足などにより却下 |

各項目に、指摘したモデルと分類理由を添えます。却下理由も成果物の一部です。利用者が親の判断を見直せるようにするためです。

## 使う場面

設計が争点の変更、見落としが心配な差分、実装者以外の視点が欲しい場合に使います。合意したモデルの数だけで出荷判断をしません。レビューが探すのは欠陥の候補であり、実アプリの確認や独立した検証は別に必要です。

> **例（本書独自の例。原文にはありません）**
>
> `/interrogate このブランチ全体を確認してください。目的は再試行時の重複送信を防ぐことです。既存の単発送信が変わらないかも見て、指摘と却下理由を示してください。`
