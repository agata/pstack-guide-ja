## create-verification-skill {#skill-create-verification-skill}

原文：{{src:skills/create-verification-skill/SKILL.md}}、{{src:skills/create-verification-skill/references/feature-map-example/README.md}}。

このスキルは、エージェントが実アプリを起動し、利用者と同じ経路で操作し、証拠を残す方法を `.cursor/skills/verify-<app>/` に作ります。利用者へ一から説明を求める前に、リポジトリから起動コマンド、操作面、既存ハーネス、観測方法、隔離方法を調べます。

Web、CLI、デスクトップ、API、モバイルなど、対象が何かを確定します。既存のテストや操作基盤があれば優先します。複数インスタンスを別ポートや別データで動かせるかも確認し、共有された利用者の環境を二重操作しません。起動できないcheckoutの上に、動くように見える説明だけを書きません。

### 生成する手順

| 節 | 含める内容 |
| --- | --- |
| `Launch` | 正確な起動方法、準備完了の判定、終了方法 |
| `Doctor` | プロセス、版、ポート、認証などの読み取り確認 |
| `Drive` | 実際のセレクターやコマンドを使う操作方法 |
| `Evidence` | 操作と結果、副作用、保存先を含む証明方法 |
| `Cleanup` | 自分が起動したものだけを終了し、証拠は残す方法 |
| `Helpers` | 付属スクリプトと実行方法 |

内部setterで結果だけ作る方法は、利用者の操作の証明にはなりません。最終画面だけでなく操作の経路を記録し、書き込まれたファイルやデータも確認します。dry-runという名前でも副作用がないとは限らないため、実際の挙動を観測します。

### 機能マップと初回の証明

`features/README.md` と、まず主要な3〜5機能のファイルを作ります。各機能は、下位機能、利用者から見た到達方法、ハーネスでの操作、注意点を持ちます。入口が複数ある場合、一つだけ動かして全機能の証明としません。

引き渡し前に、生成した手順で起動、Doctor、一つの機能操作、証拠取得、終了を実行します。終了後にも証拠が残ることを確かめます。一度も実行していないスキルは完成品ではありません。

## maintain-verification-skill {#skill-maintain-verification-skill}

原文：{{src:skills/maintain-verification-skill/SKILL.md}}。

アプリの変更で古くなる機能マップと操作手順を監査します。編集できるのは検証スキル自身のディレクトリだけです。製品コードを直したり、製品の回帰を文書変更で正常扱いにしたりしません。

まず目次と機能ファイルを照合します。機能ごとにソースを読み、説明のずれと実行確認の方法を集めます。その後、ソースに問題がなく見えても全機能を実際に一度は操作します。サーバーなら一つの管理された実行環境、短命なCLIなら隔離した各セッションを使います。

予期しない失敗の後はDoctorをやり直します。プロセスが正常でも画面が固まっているなら、既知の状態へ戻すか再起動します。失敗した試行の残骸は片付け、証拠は終了処理を越えて残します。ハーネスを直したら、その修正も実際に動かして確認します。

結果は三つです。`clean` は全機能をソースと実操作で確認し、変更不要。`changed` は検証済みの修正を一つのPRで提出。`blocked` は必要な確認や安全な提出を完了できない状態です。到達できない機能には、認証、権限、OSなどの具体的な前提と、試した経路を示します。
