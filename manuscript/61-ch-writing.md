# 文章を書く：unslopとtechnical-writing

## unslop {#skill-unslop}

原文：{{src:skills/unslop/SKILL.md}}。

`/unslop` は、文章の意味と意図した口調を保ちながら、曖昧な帰属、飾った言葉、定型的な相づち、冗長な前置き、不自然な対比などを取り除きます。「専門家は言う」なら誰なのかを示し、根拠がなければ削ります。

同じ対象を言い換え続けると、読み手は別の概念かどうか判断しなければなりません。一つの対象には一つの名前を使います。「大幅に改善」より測定値を書き、長い文は意味の単位で分けます。短縮しすぎて動詞や関係が消える文章も修正対象です。

原文には英語固有の語彙や文法規則も含まれます。日本語に適用するときは、主語と動作の明確さ、指示対象の一意性、用語の一貫性という目的を読み取ります。

> **例（本書独自の例。原文にはありません）**
>
> 修正前：「革新的な検証基盤を活用することで、開発体験を大幅に向上させます。」
>
> 修正後：「`check.mjs` は、原文リンクの欠落と未収録のスキルを検出し、問題があれば終了コード1を返します。」

後者は、読み手が何を確かめられるかを具体的に示しています。

## technical-writing {#skill-technical-writing}

原文：{{src:skills/technical-writing/SKILL.md}}。

`/technical-writing` は文書の構成、読者への文体、一文が担う情報量、解釈の曖昧さという四層を扱います。原文はDiátaxis、Google developer style、STE、Global Englishを組み合わせています。本節はそれら外部規格の全文ではなく、pstackが採用した規則の説明です。

### 文書の役割を先に選ぶ

| 種類 | 主な役割 |
| --- | --- |
| tutorial | 実際に作りながら学ぶ |
| how-to | 既知の目的へ到達する手順 |
| reference | 仕様、選択肢、制約を引く |
| explanation | 背景、理由、比較を理解する |

原文は一つの文書に一つの主な役割を求め、異なる種類の情報は分けてリンクします。PR本文とコミットメッセージには、Diátaxis以外の文体層を適用します。製品UIの文言はドキュメントとは別に、製品のコピー規則に従います。

### 読み直さなくてよい文にする

誰が何をするかを明示し、条件を操作より先に置きます。一般的な場合を先に、例外を後に説明します。手順は番号付き、並列の情報は箇条書きにします。コードの記号やパスは実名を書き、便宜的な別名を発明しません。

英語では冠詞、省略、長い名詞の連結、`only` や `not` の位置なども点検します。目的は短い文を一律に並べることではありません。一つの事実を正確に伝える長い文は残し、複数の考えが詰まった文を分けます。規則に従うことで読みにくくなるなら、別の直し方を選ぶという上位方針があります。
