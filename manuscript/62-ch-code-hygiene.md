# コードを整える：no-commentsとTypeScript

## no-comments {#skill-no-comments}

原文：{{src:skills/no-comments/SKILL.md}}、{{src:agents/comment-sicko.md}}。

`/no-comments` は、指定されたファイルや差分をComment Sickoへ渡し、結果を点検して受け入れた指摘を直します。指定がなければ、作業ツリーを含むbaseとの差分が対象です。範囲外の変更や、例外で保護されたコメントの削除は受け入れません。

### コメントの代わりに構造を直す

コードをそのまま読み上げる説明、古いコメントアウト、回避策を長く弁護する文章を減らします。自分たちのコードの意外な動作は、名前、型、抽出、再設計で明らかにできないかを考えます。`MUST KILL` は、そのような構造の修正対象を示す印です。

法的表示、変更できない外部依存の非自明な制約、公開API契約、コードでは表せない制約のIssueやRFCリンクなどは例外です。例外に当たることを、現在の経路の証拠で確認します。lintやTypeScriptの抑制も点検し、実際の不具合や安全性を守る規則を止めているなら修正対象にします。

簡単な指摘は直接直し、設計が必要なら `architect` でスケッチを作ってから、範囲内の最小の原因修正を行います。原則の引用だけで編集範囲を広げません。

### 制約の強制には別の判断がある

「消すな」「文言を変えるな」といったコメントに対して、型、実行時検査、テスト、lintで守る案を提示します。このスキルでは、その強制手段を入れる前に対話中の承認を待ち、無人実行には事前承認を求めます。承認されなかった場合の未強制の制約も報告対象です。

削除数だけでなく、復元したコメント、やり直し、構造の修正、提示した強制方法、未解決事項を返します。「コメントを減らした」という指標だけで評価する手順ではありません。

## typescript-best-practices {#skill-typescript-best-practices}

原文：{{src:skills/typescript-best-practices/SKILL.md}}、{{src:skills/typescript-best-practices/references/patterns.md}}。

型システムの原則をTypeScriptの構文に落とします。任意フィールドを寄せ集める代わりに判別可能なunionを使い、意味が違うIDにはブランド型を使います。外部入力は `any` ではなく `unknown` として受け、リポジトリのスキーマライブラリがあればそこから型を導出します。

> **例（本書独自の例。原文にはありません）**
>
> `type Upload = { kind: "waiting" } | { kind: "done"; fileId: string };`
>
> この形なら、完了状態なのに `fileId` がない組み合わせを通常の型付きコードでは作れません。

空でない配列が必要なら `[T, ...T[]]` のように構成し、通常の配列で全入力を扱える処理は過度に制約しません。`satisfies`、判別キー、網羅性の `never` を使い、検証なしの `as` で問題を隠さないようにします。型ガードも、その名前が示す条件を本当に検査している必要があります。

引数の意味が分かるオブジェクト形式を基本としますが、毎フレームの処理やパーサーなどホットパスには例外があります。実行できる対象をむやみにモックせず、実際の結果やライフサイクルを確認します。出荷コードの診断には、単なる `console.log` より文脈を持つ構造化ログを使います。
