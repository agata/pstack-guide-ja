# 依頼例とよくある失敗

![手順を使って作業する様子を描いた原著の挿絵](images/recipes.jpg)

原文：{{src:docs/guide/10-recipes-and-pitfalls.md}}。

ここに掲載する依頼文は本書独自の日本語例です。実際のパス、制約、完了条件に置き換えて使います。

## 知らない仕組みを理解する

> **例（本書独自の例。原文にはありません）**
>
> `/how 初期化の入口から設定が利用されるまでを説明してください。その後 /why で、最近変更した理由と過去の不具合を調べてください。`

現在の動作と過去の理由を分けます。検索できなかった情報源も読み、説明の範囲を把握します。

## 設計を比較する

> **例（本書独自の例。原文にはありません）**
>
> `/arena インポートAPIの案を比較してください。呼び出し側の使いやすさ、失敗の扱い、保守時に追う状態を重視します。`

同じ課題への複数案を比較するなら `arena`、別々の領域を網羅するなら `swarm` です。候補数を増やしても、課題や比較基準が曖昧なら良い選択にはつながりません。

## レビューと修正を分ける

> **例（本書独自の例。原文にはありません）**
>
> `/interrogate ブランチ全体をレビューしてください。今回は変更せず、実際の回帰とその根拠、却下した指摘の理由を示してください。`

指摘をすべて受け入れる必要はありません。現在の目的に照らして、修正する価値と費用を判断します。

## ずれた作業を戻す

> **例（本書独自の例。原文にはありません）**
>
> `今回の目的は再現までです。修正はまだ依頼していません。再現手順と確認した状態を返してください。`
>
> `ビルド結果ではなく、実際の保存操作と保存された値で確認してください。`

会話に目的が残っているなら、訂正は短くて構いません。目的と確認対象を戻します。

## 陥りやすい点

| 失敗 | 見直すこと |
| --- | --- |
| スキルを全部順番に列挙する | 目的と制約を示し、プレイブックに順序を任せる |
| 「良くして」で長時間走らせる | 合否を決められる指標や成果物を定める |
| 複数担当が同じworktreeへ書く | それぞれの書き込み先を分ける |
| `auto` をモデル名として扱う | 親モデルを継承する別名だと理解する |
| ビルド成功で完了とする | 利用者の実操作と結果を確認する |
| スキルを文章だけ直して出す | 参照、登録条件、構造の検査を通す |
| 過去の検証を新しいheadへ流用する | 検証した差分と現在の差分を対応させる |

一つの小さな仕事で、依頼、TODO、検証、報告を通してみると、どの段階で追加の指示が必要かを把握できます。
