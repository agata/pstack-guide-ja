# 用語集

本書では同じ概念に同じ名前を使います。英語の識別子は原文のまま残し、意味が近い語を区別するために必要な箇所で英語を併記します。

## 基本用語

| 語 | 意味 |
| --- | --- |
| スキル（skill） | 特定の仕事の進め方を定めた指示 |
| プレイブック（playbook） | 仕事全体を段階へ分け、スキルを組み合わせる手順 |
| 原則（principle） | 設計や実行時の判断基準 |
| ルール（rule） | 規則。またはCursorで適用される設定ファイル |
| 検証（verification） | 主張を実際の成果物や実行結果で確かめること |
| バリデーション（validation） | 入力や構造が条件を満たすかの検査。文脈によって広い意味もある |
| 再現（reproduction） | 同じ条件と操作で対象の症状を観測すること |
| 基準（baseline） | 変更前の比較対象となる測定や成果物 |
| 完了条件（done predicate） | 完了したかを検査できる条件 |
| 判定（verdict） | 証拠に基づく合否や状態の判断 |
| ゲート（gate） | 次の段階へ進むために満たす条件 |
| 証拠（evidence / receipt） | 主張を確かめるログ、画像、値、結果など |
| 成果物（artifact） | コード、文書、記録、画像など実際に出力したもの |
| 操作面（surface） | 利用者が触るUI、CLI、APIなど |
| ハーネス（harness） | 対象を起動・操作・測定するための実行基盤 |
| 機能マップ（feature map） | 利用者の機能、到達方法、確認方法を整理した資料 |
| worktree | 一つのGitリポジトリに追加する独立した作業ディレクトリ |
| スタック（stack） | 親ブランチをbaseとするPRの連鎖 |
| frontier | スタックで現在処理すべき最下位の未マージPR |
| head SHA / base SHA | 比較する先端と土台のコミット識別子 |
| patch-id | 差分の内容を識別するGitの値。コミットSHAとは異なる |
| 所有者（owner） | 作業やPRのライフサイクルに責任を持つ担当 |
| 調整役（coordinator） | 分担、結果の統合、判断、進捗を受け持つ担当 |
| レーン（lane） | 独立した検証シナリオや観点の担当 |
| 冪等性（idempotence） | 再実行しても同じ正しい終状態へ収束する性質 |
| 影響範囲（blast radius） | 変更が別の利用先や動作へ及ぼす範囲 |
| 回帰（regression） | 変更によって以前の正しい動作が壊れること |
| 盲検（blinding） | 候補や審査役から、判断を偏らせる評価情報を隠すこと |

## 混同しやすい用語

| 組み合わせ | 区別 |
| --- | --- |
| `how` / `why` | 現在の動作と、その形になった理由 |
| `teach` / `bro` | 調べて理解を助けることと、直前の説明の言い換え |
| `recall` / `session-pickup` | 最近の複数会話の文脈復元と、特定作業の引き継ぎ |
| `arena` / `swarm` | 同じ課題の案を統合することと、分担や競争を集約すること |
| `babysit` / `shipping` | マージ可能に整えることと、検証してマージすること |
| `autopilot-full` / `autopilot-stack` | 独立PRをマージすることと、検証済みスタックを引き渡すこと |
| `runtime-forensics` / `trace-forensics` | 動いている対象を計測することと、取得済み記録を分析すること |
| 実装者 / 検証者 | 作った担当と、独立に正しさを確かめる担当 |

## 状態を読み違えない

`PASS` は指定された範囲の合格です。未担当の範囲まで保証しません。`BLOCKED` は前提や環境が足りず進めない状態です。`INCONCLUSIVE` は結果から合否を判定できない状態です。どちらも合格へまとめません。

`merge-ready` はマージ条件がそろった状態で、`MERGED` は実際に取り込まれた状態です。`code-ready` は出荷するコードが固まり、独立検証のラウンドを始めるための報告です。これらは同じ完了段階ではありません。
